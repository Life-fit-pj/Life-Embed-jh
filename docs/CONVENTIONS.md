# 작업 규칙

기능을 더하거나 성능을 고치는 작업에 공통으로 적용한다.
`AGENTS.md`·`CLAUDE.md`와 겹치면 그쪽이 우선이다.

## 작업 전

- 작업 브랜치를 새로 만든다: `feat/<작업-이름>` (예: `feat/tool-eval`). `main`에 직접 커밋하지 않는다.
- 손대기 전에 기준선(baseline)을 먼저 잰다. 기준선 없이 개선했다고 쓰지 않는다.

## 측정

- 같은 평가셋·같은 필터·같은 조건에서 전후를 잰다. 평가 스크립트를 고쳤다면 기준선도 다시 잰다.
- 표본이 작으면 부트스트랩 신뢰구간을 같이 적는다. 구간이 겹치면 "개선"이 아니라 "동률"로 기록한다.
- 효과가 없거나 나빠진 결과도 지우지 않고 이유와 함께 남긴다.
- 요금이 드는 검사(LLM 호출 · 유료 임베딩)는 CI에 넣지 않는다. 사람이 원할 때 돌리는 명령으로 둔다.

## 결과 기록

작업마다 `docs/` 아래에 다음 형식으로 남긴다.

```markdown
## <작업 이름> — YYYY-MM-DD
- 왜: 해결하려는 문제
- 무엇을: 구현 요약, 핵심 파일 경로
- 측정: 기준선 → 결과 (평가셋, 표본 수, 모델, 신뢰구간)
- 남은 것: 안 한 것, 한계
```

README에 결과를 넣을 때는 그래프·도식 이미지로 넣는다 (텍스트 ASCII 도표 금지).

## 커밋

- 기능 1개 = 커밋 1개. 메시지는 `feat:`·`fix:`·`docs:` 접두사 + 한국어.
- 비밀값(`.env`, API 키)은 커밋하지 않는다. 새 환경변수는 이름만 문서에 적는다.
- 테스트가 통과하지 않으면 끝내지 않는다.
