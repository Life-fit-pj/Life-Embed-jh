# 채팅 도구 선택 평가

## 도구 선택 정확도 (Function Calling) — 2026-10-13

- **왜**: 채팅 Planner(`chat_plan_node`)가 도구 7종 중 맞는 것을 고르는지 잴 방법이 없었다.
  도구를 잘못 고르면 답이 아무리 매끄러워도 근거가 틀린다.
- **무엇을**
  - `data/golden/tool_select.csv` — Golden Set 60문항. 도구별 6~9문항, 도구 불필요 16문항
    (비회원이 회원 전용 기능을 묻는 3문항 포함), 도구 2개 6문항, 동네 비교 2문항.
  - `data/golden/tool_select_holdout.csv` — 처음 보는 문항 30개(held-out). 2차 수정 **전에** 작성했고,
    도구 설명을 고칠 때는 보지 않는다. 일반화를 확인하는 용도다.
  - `pipeline/golden_tools.py` — 실제 경로인 `chat_plan_node()`를 그대로 불러 고른 도구 이름을 모은다
    (도구는 실행하지 않아 DB를 안 읽는다). 정확 일치율(+95% 부트스트랩 구간), 도구별 precision/recall,
    도구 불필요 정답률, 회원 전용 도구 오용 건수, 2회 실행 불일치율, 혼동 표를 낸다.
  - `tests/test_golden_tools.py` — 채점 함수만 검사한다(Claude 호출 없음).
- **실행**: `py -m pipeline.golden_tools --twice` · `py -m pipeline.golden_tools --holdout --twice`
  (각각 Claude 120번 · 60번 — 요금이 들어 CI에는 넣지 않는다)

### 측정

조건: Claude Haiku 4.5(`claude-haiku-4-5-20251001`), 대화 기록 없음, 추천 동네 5곳 고정.
모든 버전을 두 평가셋에서 `--twice`로 두 번씩 돌렸다. 2회 실행 불일치율은 모든 측정에서 0%였다.

| 지표 | v0 원래 설명 | v1 1차 수정 | v2 2차 수정 |
|---|---|---|---|
| **60문항** 정확 일치율 (95% CI) | 86.7% (76.7–95.0) | 90.0% (81.7–96.7) | 86.7% (76.7–95.0) |
| 60문항 도구 불필요 정답률 | 93.8% | 81.2% | 87.5% |
| **held-out 30문항** 정확 일치율 (95% CI) | **90.0% (76.7–100)** | 83.3% (70.0–93.3) | 83.3% (70.0–96.7) |
| held-out 도구 불필요 정답률 | 90.0% | 90.0% | 90.0% |
| 회원 전용 도구 오용 (두 셋 모두) | 0건 | 0건 | 0건 |

**판정: 세 버전 모두 동률.** 모든 신뢰구간이 겹친다. 처음 보는 문항에서는 원래 설명(v0)이 가장 높았다.
→ **도구 설명은 v0로 되돌렸다.** 코드에 남은 변경은 평가 도구뿐이다.

### 무엇이 일어났나

| 버전 | 고친 것 (60문항에서 틀린 유형만 보고) | 60문항에서 | held-out에서 |
|---|---|---|---|
| v1 | 찜=좋아요, 회원 기준 vs 찜 기준, 종류 개수 vs 세부 분류, 관리비·미세먼지 | 찜·회원 문항이 고쳐졌다. 대신 개수 도구에 넣은 "많아·있어" 규칙이 넓어 "안전한 편이야?"·"학군 배정은?"까지 도구로 끌어갔다(도구 불필요 93.8 → 81.2%) | 90.0 → 83.3%. 찜 비교·버스 기준 재정렬을 새로 놓쳤다 |
| v2 | v1의 넓은 규칙을 빼고 "지표·학군 질문엔 쓰지 않는다"를 개수 도구 둘에 붙임 | 과잉 호출은 일부 줄었지만(81.2 → 87.5%) "학원 몇 개야?"를 세부 분류 도구로 보내는 새 실수가 생겼다(개수 recall 89 → 56%) | 83.3% 그대로 |

**배운 것**: 틀린 문항을 보고 설명을 고치면 그 문항은 고쳐지지만, 다른 곳에서 비슷한 수의 새 실수가 생겼다.
60문항만 봤다면 v1을 "86.7 → 90.0% 개선"으로 기록했을 것이다. 처음 보는 문항으로 재고 나서야
과적합(60문항 +3.3%p, held-out −6.7%p)이 드러났다.

### 남은 것

- **설명 수정으로는 더 올리기 어렵다.** 남은 실수(찜·미세먼지·개수 vs 분류)는 매번 다른 곳으로 옮겨 다녔다.
  다음 수단은 구조 변경이다. 예: "찜·좋아요" 같은 낱말은 LLM 판단 전에 키워드 규칙으로 먼저 라우팅,
  또는 개수 도구 둘을 `kind`가 선택인 도구 하나로 합쳐 헷갈릴 선택지 자체를 없애기.
- **표본이 작다.** 60·30문항이면 신뢰구간 폭이 ±10%p 안팎이라 3%p 차이는 가릴 수 없다.
  같은 문항의 짝 비교(McNemar)를 쓰거나 문항을 늘려야 작은 개선을 판정할 수 있다.
- 도구 인자(gu·dong·kind)가 맞는지는 재지 않았다. 이름만 본다.
- 대화 기록이 있는 질문("거기는?")은 문항에 없다.
- held-out 30문항은 v1 결과를 본 뒤에 v2를 만들었다. v2 규칙에 held-out 문구는 넣지 않았지만
  틀린 유형을 이미 본 상태였다는 점은 밝혀 둔다.

### 이력서에 넣을 한 줄

측정 기준이 없던 Function Calling 도구 선택을 **Golden Set 60문항 + held-out 30문항**으로 평가하는 체계를 만들어,
기존 문항에서 86.7% → 90.0%로 오른 것처럼 보이던 도구 설명 수정이 **처음 보는 문항에서는 90.0% → 83.3%로 떨어진 과적합**임을
잡아내고 원래 설명을 유지
